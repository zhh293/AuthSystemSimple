# Design: Refresh Token Family Lifecycle

`oauth_refresh_token_family` stores family ID (the SAS authorization ID), client, subject, current HMAC digest, absolute expiry, and revocation state. `oauth_refresh_token_history` stores each digest with `ACTIVE` or `USED` status and timestamps. Neither table stores a raw refresh token.

`FamilyAwareRefreshTokenGenerator` wraps the library refresh-token generator. On initial authorization-code exchange it creates a family using the generated token's expiry. On refresh it generates a candidate, locks the family row, checks the old digest and expiry, marks the previous history row used, and updates the current digest plus history in one database transaction. The returned token's expiry is capped at the family expiry. A stale digest revokes the family and raises `invalid_grant`.

`DigestingJdbcOAuth2AuthorizationService` checks token history before normal SAS lookup. A consumed token triggers family revocation and a credential-safe audit record. It also rejects access-token lookups when the family is revoked or expired, which makes opaque-token introspection and UserInfo fail closed. SAS's standard token revocation flow persists refresh-token invalidation; the authorization service marks the family revoked on that save.

The logout controller invokes the TGC Dubbo service, which reads the cached session subject without the account-freshness gate, revokes all of that subject's token families, and deletes the TGC independently so one storage failure does not skip the other revocation. Directory account disablement revokes subject families in the same database transaction as the account update and cursor advancement. SAS authorization writes and Redis session deletion are separate operations; failures fail closed for opaque-token lookup, but acceptance still requires runtime concurrency and failure-injection verification.

Expired family/history rows and SAS authorization records are deleted in bounded batches after a configurable retention interval (30 days by default). An authorization is eligible only when every token/code expiry column is null or older than the retention cutoff. This keeps refresh replay history available through retention and prevents cleanup from making a still-valid access token active. Expiry indexes support the scheduled authorization-table scan.

Token-storage HMAC rotation uses one active key plus an ordered list of previous keys. Every write uses only the active key; reads compute candidate digests with the active key and each previous key. This preserves existing opaque credentials and family replay history without storing key identifiers beside digests. Operators stage a new key on every node as a previous key, deploy and verify the ring consistently, then promote it to active while retaining the old active key as previous. Remove a previous key only after the maximum refresh-family lifetime, access-token lifetime, and configured history-retention window have elapsed since promotion, and after all nodes use the same active key. Removing it sooner fails closed for affected tokens and can prevent replay lookup. Key values must be unique and each at least 32 UTF-8 bytes; production configuration enforces these constraints.
