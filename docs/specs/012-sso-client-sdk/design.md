# Design: SSO Relying Party Client SDK

## Modules and boundary

`sso-client-core` owns typed properties, trusted OIDC metadata/JWKS, protocol HTTP calls, PKCE transactions, token validation, application token lifecycle, cookie helpers and extension APIs. `sso-client-spring-boot-starter` supplies conditional Boot auto-configuration, route/filter integration and production Redis adapters. Both are independent artifacts in the existing Maven reactor. The SDK is an RP and does not depend on `sso-contracts`, server persistence, Dubbo, or the SSO database.

## Protocol

Issuer is configured out of band and normalized once. Discovery and JWKS are fetched only from the trusted issuer metadata, with bounded caches and a bounded stale-key window. Login creates independent cryptographically random state and nonce, binds the transaction to a random HttpOnly browser cookie, and stores it with a short TTL. Spring Security's `OAuth2AuthorizationRequest` and `OAuth2AuthorizationRequestCustomizers.withPkce()` generate the authorization-code request, verifier and S256 challenge; the verifier is retained only in the server-side transaction. Redis transaction ciphertext is AEAD-bound to both client ID and state digest. Callback consumes state atomically before code exchange; it validates browser binding and the exact callback transaction, then delegates authorization-code and refresh token requests, grant parameters, confidential-client authentication and OAuth token-response conversion to Spring Security OAuth2 Client. The SDK applies its response-size cap and additional bounds/scope checks to the converted response. ID tokens are validated against the configured issuer and trusted keys before principal mapping. A returned scope must be a subset of requested scopes; if omitted, the requested scopes apply. Before the extension mapper runs, profile claims are retained only when `profile` was granted and email claims only when `email` was granted. RFC 7009 refresh-token revocation is a bounded form POST because Spring Security OAuth2 Client has no revocation response client.

The authorization transaction is one-time and the code exchange is never retried. Redirect targets are normalized same-origin relative paths; protocol callback URI is a fixed configured registration. Error responses to browsers are generic and carry a correlation identifier only. A refresh response ID Token is validated and remapped under the effective granted scopes; without an ID Token the SDK retains the existing verified principal.

## Application session storage

The access token cookie contains the opaque SSO access token and is scoped to the RP host. Its HMAC-SHA-256 digest is the only lookup identifier used in Redis. The mapping stores the minimal principal, access-token expiry, AES-GCM encrypted refresh token, encryption key id, client/issuer identity, fixed refresh-family expiry, the effective granted scopes, and a SHA-256 digest of the login nonce. The nonce digest lets the SDK check it if a refresh response contains an ID Token without retaining the original nonce. Refresh requests use the persisted granted-scope set as their ceiling; an omitted scope response retains that set instead of restoring configured scopes. Refresh ID Tokens are validated against trusted keys, issuer, audience/azp, time, the existing subject, and the original nonce when present. Redis TTL is capped at family expiry plus cleanup grace; cleanup grace is for record collection only and never extends authentication. Every lookup, including a live AT and a rotation-overlap lookup, enforces family expiry. Refresh uses a digest-scoped distributed lock and atomic compare-and-set mapping replacement; replacement succeeds only while the old token is still the user's current mapping, so a late refresh cannot resurrect a logged-out or superseded session. Before sending a refresh request, the SDK atomically claims a one-time marker keyed by the old RT's HMAC fingerprint and retains it through family expiry plus cleanup grace; Redis stores a second HMAC of that fingerprint, never the RT itself. In Redis mode, the marker survives mapping deletion and process restart. If the marker already exists or its write acknowledgement is uncertain, that invocation fails closed without sending the old RT. The lock wait is capped at 8 seconds and the completed-rotation overlap mapping lasts 10 seconds, so a waiter has time to read the rotation result after the lock is released. An overlap is usable only if the current AT remains beyond refresh skew and the family is still active. The lock lease is derived from two bounded discovery/token HTTP operations plus a safety margin. No old refresh token is retried after an uncertain rotation outcome. If replacement write acknowledgement or read-back is uncertain, the SDK deletes both candidate mappings with current-index comparison and best-effort revokes the newly issued refresh token. Redis outage is fail-closed in production. Bounded local stores are available only through an explicit single-instance profile and serialize composite token-map changes and lock ownership; their marker is process-local and does not survive restart.

## Spring integration

The starter is opt-in (`sso.client.enabled=true`). Its auto-configuration creates beans only when enabled and uses conditional-on-missing-bean for supported extension points. It contributes an SDK filter/registrar within the host application's chain and does not declare or replace `SecurityFilterChain`. Actuator remains an optional host dependency; only when present does the SDK register its readiness indicator, and endpoint exposure stays under host control. SDK-owned routes are explicit and route conflict/startup validation is performed before serving traffic. CSRF remains owned by Spring Security and logout requires POST; the controller also fails closed with 403 if the Spring Security CSRF filter did not expose a `CsrfToken` request attribute.

## Logout and operations

Local logout atomically takes and removes the subject/client current record before best-effort remote revoke, then decrypts the refresh token from that returned record. This ensures a refresh that wins the race just before logout is the token revoked, and prevents a late refresh from restoring the logged-out mapping. The application cookie is cleared and credentials are never exposed. The initial SDK does not implement global SSO logout or claim cross-application logout propagation. Remote failure cannot restore local state. Metrics use fixed outcome/endpoint/status labels and exclude tokens, state, user identifiers, email and arbitrary redirect URLs.

If callback processing has already persisted a session but cannot issue the AT cookie or complete its redirect, the controller locally logs out that just-created session and clears any partially written AT cookie before returning the generic failure.

If refresh rotation succeeds but the filter cannot issue the replacement AT cookie, it clears the current security context, logs out the rotated mapping, clears the browser cookie, and stops the protected request before application code runs.

## Delivery sequence

First deliver typed contracts, safe configuration and core protocol/session services; then Redis/local persistence and concurrency behavior; then opt-in Spring Boot integration and example; finally run reactor compilation and protocol/storage acceptance tests on Java 17, document migration and dependency version alignment. Any behavior that needs deployed issuer, Redis cluster or secret manager remains explicitly identified as deployment acceptance rather than inferred from unit evidence.
